# 本番に置く

**置くのは次の 3 つだけです。**

| もの                 | どこから来るか                        |
|----------------------|---------------------------------------|
| 実行ファイル         | `cargo build --release`               |
| `.env`               | 手で置く。`.env.example` をもとに書く |
| 書き込める `storage/` | `./myapp storage:init` で作る         |

## 置くもの

```
/opt/myapp/
├── myapp          リリースビルドの実行ファイル
├── .env           設定
└── storage/       書き込み先（storage:init が作る）
```

`public/`・`config/`・`resources/`・`routes/` は **置きません。** 全部バイナリに入っています。

リリースビルドの実行ファイルは **約 6.3 MB** です（`features = ["sqlite"]` のとき）。

## 手順

```sh
# 1. 作る
cargo build --release

# 2. 置く。動いている実行ファイルには上書きできないので、名前を変えてから置く
mv /opt/myapp/myapp /opt/myapp/myapp.old
cp target/release/myapp /opt/myapp/myapp

# 3. 初回だけ
cd /opt/myapp
./myapp storage:init
./myapp key:generate

# 4. 表を作る（デプロイ時に1回。各プロセスの起動時には実行しない）
./myapp migrate

# 5. 起動
./myapp serve --port 8001
```

**動いている実行ファイルへの上書きコピーは失敗します**（Linux は `Text file busy`、
Windows は使用中エラー）。`mv` で入れ替えてください。
入れ替えても、動いているプロセスは **古い版のまま動き続けます。**

## 置き場所の決め方

`bengara` は、起動したときに「基準ディレクトリ」を決めます。
`.env`・`storage/`・`public/` はここから探します。

| 順 | 見るもの                       | 条件                                      |
|----|--------------------------------|-------------------------------------------|
| 1  | `APP_BASE_PATH`                | **絶対パスのみ。** 相対なら起動しない       |
| 2  | `CARGO_MANIFEST_DIR`           | `cargo run` で動かしたとき                 |
| 3  | 実行ファイルのあるディレクトリ | **そこに `.env` か `storage/` があるとき**  |
| 4  | カレントディレクトリ           | **そこに `.env` か `storage/` があるとき**  |
| 5  | どれも決まらない               | **起動しません**                           |

**決まらなければ起動しません。** カレントディレクトリに落として動き出すと、
`.env` が読まれないまま、見当違いの場所に `storage/` を作ってしまうためです。

```
エラー: 基準ディレクトリが決まりません。
探した場所:
  実行ファイルの隣: /opt/myapp
  カレントディレクトリ: /home/alice
どちらにも .env と storage/ がありません。
直し方（どちらか）:
  1. 実行ファイルの隣に .env を置き、cargo artisan storage:init を実行する
  2. 環境変数 APP_BASE_PATH に絶対パスを指定する
```

起動したら、使っている絶対パスがログに出ます。

```
INFO 基準ディレクトリ /opt/myapp（実行ファイルの隣）
INFO storage /opt/myapp/storage
```

いつでも `about` で確かめられます。

```sh
./myapp about
```

```
bengara           0.1.0
アプリ名          myapp
環境              production
デバッグ表示      なし
URL               https://example.com
APP_KEY           あり
基準ディレクトリ  /opt/myapp（実行ファイルの隣）
storage           /opt/myapp/storage
public            /opt/myapp/public
言語              ja / ["ja"]
セッション        file
キャッシュ        file
メール            log
停止の上限        30 秒
マイグレーション  6
シーダー          1
ジョブ            2
自作コマンド      2
```

**`APP_KEY` の値は出しません。** 設定されているかどうかだけです。

## `storage/` を作る

```sh
./myapp storage:init
```

作るのは **7 つ**です。

| 作るもの                     | 用途                       |
|------------------------------|----------------------------|
| `storage/app`                | `Storage` の `local`       |
| `storage/app/public`         | `Storage` の `public`      |
| `storage/framework`          | 下の 3 つの親              |
| `storage/framework/cache`    | キャッシュ                 |
| `storage/framework/schedule` | 定期処理の前回時刻         |
| `storage/framework/sessions` | セッション                 |
| `storage/logs`               | ログ・メールのログ         |

| 決めごと         | 内容                                      |
|------------------|-------------------------------------------|
| 何度でも実行可   | あるものは触りません                       |
| Unix の権限      | **0700**（所有者だけが読み書きできる）     |
| 起動時には作らない | **デプロイ時に1回**だけ実行してください    |

**起動時に自動で作りません。** 設定を間違えたプロセスが、空の `storage/` を作って
動き出すのを防ぐためです。

場所を変えたいときは `APP_STORAGE_PATH`（**絶対パスのみ**）を指定します。

```
APP_STORAGE_PATH=/var/lib/myapp/storage
```

## 止める

| OS      | 受け付ける合図                                                       |
|---------|----------------------------------------------------------------------|
| Unix    | SIGTERM、SIGINT（Ctrl+C）                                            |
| Windows | Ctrl+C、Ctrl+Break、コンソールを閉じる操作、ログオフ、シャットダウン |

受け取った後の動きは **全 OS で同じ**です。

1. 待ち受けを閉じ、新しい接続を受け付けない。
2. 処理中のリクエストを終える。
3. 上限時間を過ぎたら、残りを打ち切って終了する。

```
INFO SIGTERM を受け取りました
INFO 処理中のリクエストが終わるまで待ちます（上限 30 秒）
INFO POST /api/login -> 200 (9729 ms)
bengara: 終了しました
```

| 設定                   | 既定 | 意味                      |
|------------------------|------|---------------------------|
| `APP_SHUTDOWN_TIMEOUT` | `30` | 上限の秒数。**`0` は無制限** |

打ち切ったときは警告が出ます。

```
WARN 30 秒たったので、残りの接続を打ち切ります
```

**30 秒を超えるリクエストは切られます。** 長い処理は [キュー](queue.md) に回してください。

**Windows のサービス停止要求は受け取れません。** サービスとして登録する仕組みが必要なためです。
`nssm` のようなサービスホストを使うと、停止時に強制終了になります。

## プロセスを2つ動かす

更新中も止めないために、同じバイナリを **別のポートで2つ**動かし、前段のプロキシで
振り分けます。

```
          ┌─ 127.0.0.1:8001  myapp（プロセス1）
nginx ────┤
          └─ 127.0.0.1:8002  myapp（プロセス2）
```

```sh
./myapp serve --port 8001 &
./myapp serve --port 8002 &
```

| 守ること                       | 理由                                                   |
|--------------------------------|--------------------------------------------------------|
| **`storage/` は同じ場所を指す** | セッションとキャッシュを共有するため                    |
| `SESSION_DRIVER=file`          | `memory` はプロセスをまたげません                       |
| `CACHE_DRIVER=file`            | 同上                                                   |
| `migrate` はデプロイ時に1回     | 各プロセスの起動時に流さない                            |
| スケジューラは1つだけ           | Web のプロセスごとに動かすと、同じ処理が重複して走ります |

3つ以上に増やす意味はあまりありません。Rust は1プロセスで全コアを使うので、
増えるのは DB の接続数とメモリだけです。

### 前段の設定（nginx の例）

```nginx
upstream myapp {
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
}

server {
    listen 80;
    location / {
        proxy_pass http://myapp;
        # 止めたプロセスにつながらなければ、もう一方へ送る
        proxy_next_upstream error timeout;
    }
}
```

**`POST` は送り直されません。** nginx は既定で、冪等でないリクエストを送り直しません。
止めたプロセスへの `POST` は失敗します。`non_idempotent` を足せば送り直しますが、
こんどは **処理が二重に走る危険**があります。どちらを取るかは運用で決めてください。

### 接続元のアドレスを伝える

前段にプロキシを置くと、本体から見える接続元はプロキシのアドレスになります。
回数の制限（`throttle`）は接続元のアドレスで数えるので、全員が同じ枠を共有してしまいます。

そこで `.env` に `TRUSTED_PROXIES` を書きます。

```
TRUSTED_PROXIES=127.0.0.1
```

| 決めごと                   | 内容                                                              |
|----------------------------|-------------------------------------------------------------------|
| 見るヘッダー               | `X-Forwarded-For` と `X-Real-IP`                                  |
| 見る条件                   | **接続元がこの一覧に載っているときだけ**                          |
| 空のとき（既定）           | **どちらのヘッダーも見ません。** 接続元のアドレスで数えます       |
| 書き方                     | IP アドレスをカンマで並べる。`*` で全部を信じる                   |
| 範囲指定（CIDR）           | **書けません。** `10.0.0.0/8` のような書き方は使えません          |
| 読めない値                 | 警告を出して無視します                                            |

**前段にプロキシを置くときだけ設定してください。** 無条件に信じると、
偽のヘッダーを送るだけで回数の制限を回せます。

### 更新の手順

1. 新しいバイナリを `mv` で入れ替える。
2. 必要なら `migrate` を実行する（**旧版でも動く変更だけ**）。
3. 1つ目のプロセスを止め、新しいバイナリで起動し、`/up` が 200 を返すまで待つ。
4. 2つ目も同じ手順で入れ替える。

更新中は旧版と新版が同時に動きます。DB の形を変えるときは、
**列やテーブルの追加は先に**、**削除は全プロセスの更新後に**行ってください。

## `migrate` の同時実行

`migrate` 系は、実行の前に DB に札を置きます。
**2つ目は止まります。**

```
エラー: 別のプロセスがマイグレーションを実行中です（web01:1416 が 2026-10-05 11:32:21 に開始）。
終わってからもう一度実行してください。
途中で落ちて札が残っているときは、`migrate:unlock` で消せます。
```

途中でプロセスが落ちると札が残ります。 **時間で自動には外しません**
（長いマイグレーションの最中に二重に走る恐れがあるため）。

```sh
./myapp migrate:unlock
```

```
札を外しました（web01:1416 が 2026-10-05 11:32:21 に取ったもの）。
```

札は `migration_locks` 表に置きます。マイグレーションを書く必要はありません。

## 準備完了の確認

`/up` は、起動の処理がすべて終わってから 200 を返します。

```rust
// bootstrap/app.rs
.with_routing(|r| r.web(crate::routes::web::routes).health("/up"))
```

```sh
curl -sf http://127.0.0.1:8001/up || echo "まだ"
```

無償版の nginx に能動的なヘルスチェックはありません。更新の手順の側で確かめてください。

## 常駐させる（systemd の例）

```ini
[Unit]
Description=myapp (port 8001)
After=network.target

[Service]
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/myapp serve --port 8001
Restart=always
# SIGTERM を送ってから、この秒数まで待つ（APP_SHUTDOWN_TIMEOUT より長くする）
TimeoutStopSec=40
User=myapp

[Install]
WantedBy=multi-user.target
```

キューの worker とスケジューラは、Web とは別に動かします。

```ini
# キュー（1つ以上）
ExecStart=/opt/myapp/myapp queue:work
```

```
# スケジューラ（cron。1分ごとに1つだけ）
* * * * * cd /opt/myapp && ./myapp schedule:run >> /dev/null 2>&1
```

## 本番で気をつけること

| 項目                 | すること                                                       |
|----------------------|----------------------------------------------------------------|
| `APP_ENV`            | `production` にする。`migrate:fresh` などが `--force` 無しで止まる |
| `APP_DEBUG`          | `false` にする。エラー画面に詳細を出さない                      |
| `APP_KEY`            | `key:generate` で作る。**64 文字以上が必須**（下の節）           |
| `TRUSTED_PROXIES`    | 前段にプロキシを置くときだけ設定する（上の節）                   |
| `HASH_ITERATIONS`    | 下げたままにしない。既定（120,000）以上にする                    |
| `storage/` の権限    | `storage:init` が 0700 にします。所有者をアプリの実行ユーザーに  |
| ログ                 | 標準出力に出ます。ファイルに書くならプロセスごとに分ける         |

## APP_KEY

`APP_KEY` は **64 文字以上**が必要です。
短いと、セッション・署名付き URL・暗号化を使う最初のリクエストでエラーになります。

```sh
./myapp key:generate          # 作って .env に書き込む
./myapp key:generate --force  # すでにある値を上書きする
```

使うときは、用途ごとに別の鍵を作ります（`hmac_sha256(APP_KEY, 用途名)`）。

| 用途           | 用途名                |
|----------------|-----------------------|
| セッション     | `bengara:session`     |
| 署名付き URL   | `bengara:signed-url`  |
| 暗号化         | `bengara:encryption`  |

**入れ替えると、次のものが無効になります。**

- いまあるセッション（全員がログアウトされます）
- 暗号化して保存した文字列（読めなくなります）
- 配布済みの署名付き URL（照合に失敗します）

鍵の作り方を変えたので、**以前の `APP_KEY` をそのまま使っても同じことが起きます。**
入れ替えは、ログアウトされて困らない時間帯に行ってください。

## 無いもの

| 項目                               | 代わりにすること                        |
|------------------------------------|-----------------------------------------|
| Windows のサービス停止要求          | ありません                              |
| 独自の停止コマンド                  | OS 標準の合図を使う                     |
| 内蔵のロードバランサ                | 前段のプロキシに任せる                   |
| systemd のソケットアクティベーション | ありません（Linux だけの仕組み）         |
| 無停止更新の自動化                  | 上の手順を自分のスクリプトに落とす       |
| `storage:link`                      | `/storage/...` で直接配信します          |
