# 本番に置く

実行ファイル 1 つを置いて動かす手順です。
止め方、止めずに更新する方法、常駐させる設定の例もここにあります。

## 手順の全体

| 手順 | すること                                  | いつ         | 詳しくは                                  |
|------|-------------------------------------------|--------------|-------------------------------------------|
| 1    | `cargo build --release` で作る            | 毎回         | [置くもの](#置くもの)                     |
| 2    | 実行ファイルを入れ替える                  | 毎回         | [入れ替える](#入れ替える)                 |
| 3    | `.env` を書く                             | 初回         | [本番の .env](#本番の-env)                |
| 4    | `./myapp storage:init` で書き込み先を作る | 初回         | [storage を作る](#storage-を作る)         |
| 5    | `./myapp key:generate` で鍵を作る         | 初回         | [本番の .env](#本番の-env)                |
| 6    | `./myapp migrate` で表を作る              | 更新のたびに 1 回 | [migrate の同時実行](#migrate-の同時実行) |
| 7    | `./myapp serve` で起動する                | 毎回         | [常駐させる](#常駐させる)                 |
| 8    | `/up` が 200 を返すのを確かめる           | 毎回         | [準備完了の確認](#準備完了の確認)         |

```sh
# 1. 作る
cargo build --release

# 2. 置く。動いている実行ファイルには上書きできないので、名前を変えてから置く
mv /opt/myapp/myapp /opt/myapp/myapp.old
cp target/release/myapp /opt/myapp/myapp

# 3〜5. 初回だけ。.env を先に置く
cd /opt/myapp
cp /path/to/.env.example .env   # 中身を本番用に直す
./myapp storage:init
./myapp key:generate

# 6. 表を作る
./myapp migrate

# 7. 起動
./myapp serve --port 8001
```

**初回は `.env` を先に置いてください。** `.env` も `storage/` も無い場所では、
`storage:init` も `key:generate` も「基準ディレクトリが決まりません」で止まります。

## 置くもの

**置くのは次の 3 つだけです。**

| もの                  | どこから来るか                        |
|-----------------------|---------------------------------------|
| 実行ファイル          | `cargo build --release`               |
| `.env`                | 手で置く。`.env.example` をもとに書く |
| 書き込める `storage/` | `./myapp storage:init` で作る         |

```
/opt/myapp/
├── myapp          実行ファイル
├── .env           設定
└── storage/       書き込み先
```

`public/`・`config/`・`resources/`・`routes/` は**置きません。**
全部が実行ファイルに入っています。

## 入れ替える

**動いている実行ファイルへの上書きコピーは失敗します。**
先に `mv` で名前を変えてから、新しいものを置いてください。

入れ替えても、動いているプロセスは古い版のまま動き続けます。
新しい版にするには、プロセスを起動し直します。

## 基準ディレクトリの決め方

起動したときに「基準ディレクトリ」を 1 つ決めます。
`.env`・`storage/`・`public/` はここから探します。

| 順 | 見るもの                       | 条件                                       |
|----|--------------------------------|--------------------------------------------|
| 1  | 環境変数 `APP_BASE_PATH`       | **絶対パスのみ。** その場所があること      |
| 2  | cargo のプロジェクト           | `cargo run` で動かしたとき                 |
| 3  | 実行ファイルのあるディレクトリ | **そこに `.env` か `storage/` があるとき** |
| 4  | カレントディレクトリ           | **そこに `.env` か `storage/` があるとき** |

**決まらなければ起動しません。** 直し方を書いたエラーが出ます。

```
エラー: 基準ディレクトリが決まりません。
探した場所:
  実行ファイルの隣: /opt/myapp
  カレントディレクトリ: /home/alice
どちらにも .env と storage/ がありません。
直し方（どちらか）:
  1. 実行ファイルの隣に .env を置き、storage:init（開発では `cargo artisan storage:init`、本番では `./<実行ファイル> storage:init`）を実行する
  2. 環境変数 APP_BASE_PATH に絶対パスを指定する
```

- `APP_BASE_PATH` は `.env` に書いても効きません。本物の環境変数で渡します。
- `--version` と `--help` は、基準ディレクトリが無くても動きます。

### いまの設定を確かめる

`./myapp about` で、いまの設定と置き場所が見られます。

```
bengara           0.1.0

public            /opt/myapp/public
言語              ja / ["ja"]

メール            log
停止の上限        30 秒

```

- `APP_KEY` の値は出しません。設定されているかどうかだけです。
- `serve` も、起動のときに基準ディレクトリと `storage` の絶対パスをログに出します。

## storage を作る

```sh
./myapp storage:init
```

`storage/` と、その下の書き込み先を作ります。
中身の一覧は [directory-structure.md](directory-structure.md) にあります。

| 決めごと           | 内容                                           |
|--------------------|------------------------------------------------|
| 何度でも実行できる | すでにあるものには触りません                   |
| Unix の権限        | 作ったものを **0700**（所有者だけ）にします    |
| 起動時には作らない | **自分で 1 回実行してください**                |

- `storage/` の所有者は、アプリを動かすユーザーにしてください。
- `storage/` が無いまま起動すると、ログに警告が出ます。
- 場所を変えるときは `APP_STORAGE_PATH` に絶対パスを書きます。

```ini
APP_STORAGE_PATH=/var/lib/myapp/storage
```

## 本番の .env

| 項目              | すること                                                             |
|-------------------|----------------------------------------------------------------------|
| `APP_ENV`         | `production` にする（下の注）                                        |
| `APP_DEBUG`       | `false` にする。エラー画面に詳細を出しません                         |
| `APP_KEY`         | `./myapp key:generate` で作る。**64 文字以上が必須**                 |
| `APP_URL`         | 公開する URL にする                                                  |
| `HASH_ITERATIONS` | 開発用に下げた値を残さない。既定（120,000）以上にする                |
| `TRUSTED_PROXIES` | 前段にプロキシを置くときだけ書く（[接続元のアドレスを伝える](#接続元のアドレスを伝える)） |

`APP_ENV=production` にすると、次の 2 つが変わります。

- 中身が消えるコマンド（`migrate:fresh` など）が `--force` を求めます。
- セッションの Cookie に `Secure` が付きます。**利用者には HTTPS で見せてください。**

```sh
./myapp key:generate          # 作って .env に書き込む
./myapp key:generate --force  # すでにある値を作り直す
```

**鍵を作り直すと、全員がログアウトします。** 暗号化して保存した値と、配った
署名付き URL も無効になります。困らない時間帯に行ってください。

項目の一覧と書き方は [configuration.md](configuration.md) にあります。
ログは標準出力に出ます。

## 止める

| OS      | 受け付ける合図                                                       |
|---------|----------------------------------------------------------------------|
| Unix    | SIGTERM、SIGINT（Ctrl+C）                                            |
| Windows | Ctrl+C、Ctrl+Break、コンソールを閉じる操作、ログオフ、シャットダウン |

受け取った後の動きは、どの OS でも同じです。

1. 待ち受けを閉じる。新しい接続は受け付けません。
2. 処理中のリクエストが終わるのを待つ。
3. 上限の時間を過ぎたら、残りを打ち切って終わる。

```
INFO SIGTERM を受け取りました
INFO 処理中のリクエストが終わるまで待ちます（上限 30 秒。もう一度合図を送ると強制終了します）
INFO POST /api/login -> 200 (9729 ms)
bengara: 終了しました
```

| 場面                      | どうなるか                                                    |
|---------------------------|---------------------------------------------------------------|
| 上限の時間                | `APP_SHUTDOWN_TIMEOUT` の秒数。既定 30。**`0` は無制限**      |
| 上限を過ぎた              | 警告を出して打ち切る。その後、裏の処理を **3 秒だけ**待って終わる |
| 待っている間に 2 回目の合図 | **待たずに終わる**（終了コード 130）。無制限のときも効きます |

- **上限より長くかかるリクエストは切られます。** 長い処理は [キュー](queue.md) に回してください。
- **Windows のサービス停止要求は受け取れません。** `nssm` のようなサービス化の道具を
  使うと、止めるときに強制終了になります。

### queue:work を止める

`queue:work` も同じ合図を受けます。

| 合図   | 動き                                                              |
|--------|-------------------------------------------------------------------|
| 1 回目 | **いま動かしている 1 件を終えてから**止まる。次のジョブは取らない |
| 2 回目 | 待たずに終わる（終了コード 130）                                  |

- `APP_SHUTDOWN_TIMEOUT` は効きません。待つのは「いまの 1 件」が終わるまでです。
- 途中で強制終了されたジョブは、`--retry-after`（既定 90 秒）の後に取り直されます。
- データベースの一時的なエラーでは、すぐには終わりません。数回やり直します。
  それでも直らなければエラーで終わるので、起動し直す設定（`Restart=always` など）は要ります。

## プロセスを 2 つ動かす

更新の間も止めないために、同じ実行ファイルを**別のポートで 2 つ**動かします。
前段のプロキシ（nginx など）で振り分けます。

```
          ┌─ 127.0.0.1:8001  myapp（プロセス 1）
nginx ────┤
          └─ 127.0.0.1:8002  myapp（プロセス 2）
```

```sh
./myapp serve --port 8001 &
./myapp serve --port 8002 &
```

| 守ること                        | 理由                                                 |
|---------------------------------|------------------------------------------------------|
| **`storage/` は同じ場所を指す** | セッションとキャッシュを共有するため                 |
| `SESSION_DRIVER=file`           | `memory` はプロセスをまたげません                    |
| `CACHE_DRIVER=file`             | 同じ理由                                             |
| `migrate` は更新のたびに 1 回   | プロセスごとの起動時には流さない                     |
| `schedule:run` は 1 か所だけ    | 同じ処理を二重に走らせないため                       |

回数の制限（`Throttle`）はプロセスごとに数えます。2 つ動かすと、上限は約 2 倍になります。

### 更新の手順

1. 新しい実行ファイルに入れ替える。
2. 必要なら `migrate` を実行する（**古い版でも動く変更だけ**）。
3. 1 つ目のプロセスを止め、新しい版で起動し、`/up` が 200 を返すまで待つ。
4. 2 つ目も同じ手順で入れ替える。

更新の間は、古い版と新しい版が同時に動きます。
表の形を変えるときは、**列や表の追加は先に**、**削除は全部のプロセスを更新した後に**行います。

### 前段の設定（nginx の例）

```nginx
upstream myapp {
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
}

server {
    listen 80;
    location / {
        proxy_pass http://myapp;
        # 止めたプロセスにつながらなければ、もう一方へ送る
        proxy_next_upstream error timeout;
    }
}
```

**`POST` は送り直されません。** nginx は既定で、やり直すと結果が変わりうるリクエストを
送り直しません。止めたプロセスへの `POST` は失敗します。
`non_idempotent` を足せば送り直しますが、処理が二重に走る危険があります。

### 接続元のアドレスを伝える

前段にプロキシを置くと、本体から見える接続元はプロキシのアドレスになります。
回数の制限は、ログインしていない人を接続元のアドレスで数えます。
そのままでは、全員が同じ枠を使ってしまいます。

`.env` に、プロキシのアドレスを書いてください。

```ini
TRUSTED_PROXIES=127.0.0.1
```

- **前段にプロキシを置くときだけ書きます。** 置かないのに書くと、
  偽のヘッダーを送るだけで回数の制限をすり抜けられます。
- 書き方と、どのアドレスを採るかは [configuration.md](configuration.md) にあります。

## migrate の同時実行

表を変えるコマンドは、実行の前に「実行中」の札を置きます。**2 つ目は待たずに止まります。**
札は `migration_locks` という表に置きます。この表は自動で作ります。

| 札を取る                                                                                           | 札を取らない                        |
|----------------------------------------------------------------------------------------------------|-------------------------------------|
| `migrate` / `migrate:rollback` / `migrate:reset` / `migrate:refresh` / `migrate:fresh` / `db:seed` / `db:wipe` | `migrate:status` / `migrate:unlock` |

```
エラー: 別のプロセスがマイグレーションを実行中です（web01:1416 が 2026-10-05 11:32:21 に開始）。
終わってからもう一度実行してください。
途中で落ちて札が残っているときは、`migrate:unlock` で消せます。
```

途中でプロセスが落ちると、札が残ります。**時間がたっても自動では外れません。**
`./myapp migrate:unlock` で外してください（[migrations.md](migrations.md)）。

## 準備完了の確認

`/up` は、起動の処理が全部終わってから 200 を返します。
`bootstrap/app.rs` の `health("/up")` が登録しています（`init` が書きます）。

```sh
curl -sf http://127.0.0.1:8001/up || echo "まだ"
```

本文は `{"status":"ok","name":"<アプリ名>"}` です。環境名は出しません。

## 前段に任せるもの

本体が自分で守るのは、次の 2 つだけです。

| 守るもの                   | 上限    | 超えたとき |
|----------------------------|---------|------------|
| リクエストの本文の大きさ   | 2 MiB   | 413        |
| 本文を読み終えるまでの時間 | 30 秒   | 408        |

次のものは持っていません。前段のプロキシで掛けてください。

| 持っていないもの                         | nginx での例            |
|------------------------------------------|-------------------------|
| ヘッダーが来るまでの待ち時間             | `client_header_timeout` |
| 使っていない接続を切るまでの時間         | `keepalive_timeout`     |
| 同時接続数の上限                         | `limit_conn`            |
| 相手ごとの回数の制限（プロセスをまたぐ） | `limit_req`             |
| HTTPS                                    | `listen 443 ssl`        |

**前段を置かずに直接公開するのは勧めません。** 上のものが無いまま外に出ます。

## 常駐させる

systemd の例です。

```ini
[Unit]
Description=myapp (port 8001)
After=network.target

[Service]
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/myapp serve --port 8001
Restart=always
# SIGTERM を送ってから、この秒数まで待つ
TimeoutStopSec=40
User=myapp

[Install]
WantedBy=multi-user.target
```

`TimeoutStopSec` は、SIGTERM を送ってから強制終了（SIGKILL）するまでの秒数です。
短いと、処理の途中で強制終了されます。

| 動かすもの   | `TimeoutStopSec` の目安                                         |
|--------------|-----------------------------------------------------------------|
| `serve`      | `APP_SHUTDOWN_TIMEOUT` ＋ 10 秒（既定の 30 秒なら 40）          |
| `queue:work` | ジョブ 1 件にかかる時間より長く（`--timeout` の秒数より長く）   |

### キューと定期処理

Web とは別に動かします。

```ini
# キューの worker（1 つ以上）
ExecStart=/opt/myapp/myapp queue:work
Restart=always
TimeoutStopSec=120
```

`--timeout`（既定 60 秒）は `--retry-after`（既定 90 秒）より短くします（[queue.md](queue.md)）。

```
# 定期処理（cron。1 分ごとに、1 か所だけ）
* * * * * cd /opt/myapp && ./myapp schedule:run >> /dev/null 2>&1
```

**`schedule:run` は 1 分ごとに呼んでください**（[scheduling.md](scheduling.md)）。

### セッションの掃除

期限切れのセッションのファイルは、ふだんの書き込みのついでに少しずつ消えます。
1 回に見るのは 500 件までです。利用者が多いところでは、全部を見る `session:gc` を
1 日 1 回ほど流してください（[session.md](session.md)）。

```
0 4 * * * cd /opt/myapp && ./myapp session:gc >> /dev/null 2>&1
```

## できないこと

- 内蔵のロードバランサと、更新を自動でやるコマンドはありません。上の手順を使います。
- 止めるための専用のコマンドはありません。OS の合図で止めます。
- `storage:link` はありません。`/storage/...` は本体が直接配信します（[storage.md](storage.md)）。

まだ無い機能の一覧は [backlog.md](backlog.md) にあります。
